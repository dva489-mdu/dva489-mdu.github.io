DVA489 — Web Security

Welcome to DVA489! This course follows a build–analyze–attack–fix approach: you will develop web applications, study how they work, attack them, and then implement and evaluate protections against the attacks you just carried out.

BUILD → ANALYZE → ATTACK → FIX → RE-TEST

The interplay between developing, attacking and protecting an application is what gives you a deep understanding of why the attacks are possible, how to exploit them, and how to protect against them.

This course covers a lot of material. Some of it will be introduced in the introductory lectures, but you are required to do a lot of reading on your own. To your aid there will be links to relevant resources and you will have the opportunity to ask questions during our supervision sessions. If your questions cover a larger topic, please contact us in advance to allow us to prepare additional material.

A fundamental security principle: never trust the client

Anything sent from a browser to a server should be treated as untrusted input. The user controls the browser and can modify URLs, parameters, form data, headers, cookies, and request bodies — so security decisions must be enforced by the server, not trusted to the client. This principle runs through the whole course: Assignment 1 demonstrates it with reflected XSS, Assignment 2 with authentication and session data, Assignment 3 with user-generated content and CSRF, and Assignment 4 with database input and cookies.

How the assignments work

You build one application per assignment, and you attack that same application — the one you just wrote yourself. An online example solution is also provided for each assignment, but it is there for inspiration and reference only (see Example solutions below), not as a separate target to attack.

  1. Build your application. Follow the assignment guide to implement the assigned web application yourself.
  2. Study the relevant vulnerability. Understand how and why the vulnerability class arises.
  3. Attack your own application. Use what you learned to find and exploit the vulnerability in the application you built.
  4. Produce a proof of attack. Document your successful attack — this is what you hand in.
  5. Patch your own application. Apply and justify appropriate protections in the application you built.
  6. Explain and submit your work. Hand in your reports and code as described under Submission requirements below.

The purpose of the assignments is not to test whether you can independently write every line of code from scratch. The purpose is to understand the application, identify vulnerabilities, successfully exploit them, and implement and justify appropriate protections. The overall quality of your assignments and the number and quality of your successful attacks contribute to your final ECTS grade.

Submission requirements

All submissions are handed in on Canvas. Hand in attack reports and other documentation as separate PDF files, and all source code in one ZIP file. Include both the original code, to allow us to replicate your attacks, and the patched source code, to allow us to verify your protection mechanism and hunt for more ways to attack your code.

Code

  • Patched code
  • package.json describing your project and its packages

Reports
  • Attack reports as separate PDF files
  • Proof of successful attacks
  • Explanation of protections

Malformed submissions

Important rules

Since you will be attacking your own web applications, there is a risk that the code you write is not vulnerable to attack. The guides try to alleviate this problem by guiding you towards a believable solution containing common security flaws. The intention is that, if you follow the instructions closely, you should end up with an application open to the selected attacks.

Early protection

Do not add security protections before they are introduced in the assignment. The vulnerabilities are intentional and are needed for the subsequent attack exercises.

You should, however, keep the application confined to the intended course environment and never deploy the deliberately vulnerable version publicly.

To ensure a detailed understanding of the inner workings of the vulnerabilities and the protection mechanisms, it is important that you implement things yourself.

Third-party libraries

Use only the libraries explicitly permitted in each assignment. Unless an assignment explicitly permits a third-party package, implement the required functionality using Node.js built-in APIs.

Inclusion of libraries that are not part of the core Node.js runtime, and not explicitly permitted by the assignment, will result in rejection of the assignment!
